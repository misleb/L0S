# The programs

Each one is the usual three files, `NAME.l0`, `NAME_test.l0` and
`main.l0`, in a directory whose place says where the program goes in the
initramfs, so that the Makefile finds it there:

| Directory | What | In the initramfs |
|---|---|---|
| `user/bin/NAME` | a command: `sh`, `cat`, `disk`, `draw`, `fonts`, `hello`, `http`, `init`, `install`, `keys`, `lsusb`, `nap`, `net`, `ping`, `play`, `random`, `spin`, `tftp`, `windows` | `/bin/NAME` |
| `user/sbin/NAME` | a driver or a service: `boot`, `uart`, `rtc`, `eeprom`, `virtio-gpu`, `hvs`, `hdmi-audio`, `usb-audio`, `audio`, `virtio-input`, `virtio-blk`, `virtio-net`, `gem`, `virtio-rng`, `rng200`, `pcie`, `xhci`, `usb-hid`, `sdhci`, `fs`, `inet`, `ntp`, `font`, `wm`, `echo`, `speech` | `/sbin/NAME` |
| `user/apps/NAME` | an app, with its bundle's source `APP.app/` beside it: `vt`, `procmon`, `widgets`, `disks`, `files`, `todo` (see [Apps](boot.md#apps)) | `/Applications/APP.app/NAME` |

A program may have more files of its own, each with its tests beside it,
as `sh` has `files.l0`, `wm` `launcher.l0` and `launching.l0`, `audio` `mixer.l0` and `settings.l0`, `files` `fsview.l0`, `inet` `packet.l0`, `segment.l0`, `tcp.l0`, `tcpstack.l0`, `dhcp.l0` and `lease.l0`, `pcie` `cfg.l0`, `virtio-gpu` `flight.l0`, `sdhci` `sd.l0`, `usb-hid` `hid.l0`, `rtc` `firmware.l0` and `zone.l0`, `hvs` `regs.l0`, `plane.l0`, `pieces.l0`, `corners.l0`, `iommu.l0`, `fw.l0`, `frames.l0`, `shown.l0`, `pending.l0` and `watch.l0`, `hdmi-audio` `mai.l0`, `iec958.l0` and `dma40.l0`, `gem` `regs.l0` and `phy.l0`, and `xhci` `trb.l0`, `ring.l0`, `ctx.l0`, `port.l0`, `regs.l0`, `core.l0`, `bus.l0` and `dwc3.l0`:
every `.l0` in its directory is part of it.

| Program | What it does |
|---|---|
| `boot` | the first stage's end, pid 1 of a two-stage inittab (see [Booting from a volume](boot.md#booting-from-a-volume)): given `root=UUID`, waits for that volume, makes it `/` if it holds `/etc/system`, and says so or why not; given `root=tmpfs`, has `install` fill the RAM file system first; starts `/etc/system`'s programs by path, and exits with the first one's status |
| `sh` | the shell, on the terminal its argument names, `console` unless given (`sh vt1` is a window's): reads commands from it; runs programs by name or path, from `/` wherever it is or from a volume, on its terminal, and waits for them, with Ctrl-C for the foreground job, unless the job asked its terminal for Ctrl-C itself, as `agent` does (the shell asks again at each prompt); has busybox's commands on files, `ls`, `cat`, `write`, `append`, `cp`, `mv`, `rm`, `mkdir`, `df`, `format`, `unmount` and `relabel`, on the initramfs and the volumes alike; also `ps`, `names`, `uptime`, `kill`, `sleep`, `echo`, `exit`, `reboot` and `dmesg`, which prints the kernel's log, a line for each message with its time since boot. `ps` lists each live process's pid, parent, the CPU it is on or last ran on, its % of one CPU over the quarter second `ps` watches (over its life if it started meanwhile; the shell's own over its life), its program, the names it serves, comma separated, `-` for none, and its state; `names` every name registered, in order, its port, and the pid and program serving it; `uptime` how long the system has run, the load averages over 1, 5 and 15 minutes, and each CPU's % busy over a second, CPU 0's with the kernel's own share (`cpu_usage`, `name_list`). Shows `/etc/motd` at start. Tells its terminal its folder as its title at each prompt, and a program's name while it waits for it (`t`, [demo.md](demo.md#terminals)). Exits with status 129 if its terminal's process exits. `sh -c LINE` runs one line of its commands on the standard input, output and error it was given, with no `/etc/motd` and no prompt (the words after `-c` joined by spaces, one pair of double quotes around them taken off), and exits with the status of the program `run` ran, 1 for a command it complained of, else 0 |
| `install` | `install VOLUME`: copies every directory and file of `/` but `/Volumes` and `/boot`, the Pi 5's boot files, onto the volume, a label or `/Volumes/LABEL`, marking each program's copy a program, and says the volume's UUID, for `root=`; refused for a volume not mounted, and for `/`'s own. `install --boot VOLUME [FROM]` makes a FAT32 volume a Raspberry Pi 5's boot partition instead: FROM's files, `/boot` unless given, copied onto it, the Pi 5's device trees among them, and `input.bin` written, an initramfs of `/` but `/Volumes`, a file at a time; it says so if the card is left with no device tree, as from a FROM without one. With `--root ROOT`, anywhere after VOLUME, the card's `cmdline.txt` says `root=` and ROOT's UUID, its other arguments kept and any `root=` replaced, so that `boot` makes ROOT `/`; refused, before anything is written, for a ROOT not mounted, with no UUID, or VOLUME itself (see [The Raspberry Pi 5](pi5.md#the-raspberry-pi-5)). `install --net fresh [--boot BOOT] [--boot-order sd,net] [--progress] SYSTEM` and `install --net update [...] [SYSTEM]` install from the release the host's proxy serves instead (`release.l0`, see [Installing from the proxy](boot.md#installing-from-the-proxy)): the release for the board `/etc/board` names, each file checked by its SHA-256 as it comes; a fresh install formats SYSTEM and BOOT first, writes `cmdline.txt` with `root=`, and seeds `/Volumes/data`; an update keeps `cmdline.txt`, `/etc/agent`'s `config` and `token`, a model the same already and every agent's file; `--boot-order sd,net` writes a `pieeprom.upd` of the release's `pieeprom.bin` with `BOOT_ORDER=0xf21` onto BOOT; `--progress` says each file as it begins and each megabyte, for the Installer |
| `uart` | the serial line's terminal, `console`: a driver for the PL011 serial port. L0 says nothing of the board, so it finds its port: of the places a PL011 is on L0's boards, QEMU's at 0x09000000 and the Raspberry Pi 5's debug UART at 0x107D001000, the first the kernel gives whose ID registers say PL011. It takes that port's receive interrupt, 33 or 153, edits lines, echoes them (unless given `noecho`), and hands a line to each process that asks. Ctrl-C drops unread input and sends a lone byte 3 to the port that asked to hear of it. What it is sent to write, it writes to the serial line |
| `vt` | Terminal, terminals in a window, as GNOME Console's, `vt [COLS ROWS]`, a window of 80×24 cells unless given. Its window draws its own decorations (`ui_open_csd`): the toolkit's header bar, the selected tab's title its title and wm's, which is what the tab's shell tells it (`t`, [demo.md](demo.md#terminals)), its folder or the program it waits for, at first the folder it starts in, `vt`'s own, with a new-tab button at its start and the close button at its end; with two tabs or more, the toolkit's tab bar under it, a click on a tab selecting it and its close button closing it; and under them the terminal, a drawing area that scrolls by rows (`UiDrawingRows`), which `vt` paints itself, the window's outline over its edges, its rows those that fit above the outline along its foot, so that the cursor's line on the last shows (the window 431 high for 24). Each tab is a terminal of its own (`tabs.l0`), named the first of `vt1`, `vt2`, and so on that no one has, which `vt` registers on a port of the tab's own; it waits on its app's port and every tab's at once, the tabs' ports the toolkit's loop's own (`ui_app_ports`, what comes on one a `UiPort` event; see [toolkit.md](toolkit.md)), and knows a tab by the port a message came on, so a tab costs no process but its shell. With the name registered, `vt` starts the tab's shell, `sh NAME`, and watches it: when it exits the tab closes, its name let go (`name_unregister`) and its port kept for the next tab, and with the last tab the window; the close button ends every tab's shell, and the window. Terminal is a `UiApp` of many windows on one port, registered as `app.vt`, which keeps its windows, `vt` each one's tabs by its id: launched again while it runs, it answers the open itself (`ui_app_opening`), opening a window more with one tab (`open`, below), and `vt` exits once its last window closes, with the status of the shell that closed it, or 0 for a close button. Its windows have at most 29 tabs between them, the loop's set at most 32 ports, the app's and the toolkit's two reply ports among them. Its messages come through the toolkit's loop, which takes what else waits with each, the tabs' first, then its windows' notices put together; a strike that comes is drawn as in any window. Each tab has the same line editing as `uart`'s, fed the characters of the keys `wm` sends while the window is in front and the tab selected. What a tab is sent to write, and the echo, it keeps as bytes (`cells.l0`): its screen, a row of cells each, a byte a cell, each row marked if a wrap, not a newline, ended it, and a ring of the last 10,000 rows scrolled off its top; output to a tab not shown is kept for when it is. The selected tab is drawn into the window's buffer, shared with `wm`, in the 8×16 font (at scale 2, cells of 16×32 in the face's Source Code Pro), in the toolkit's terminal colors, GNOME Console's white on `1e1e1e`: output at the bottom by copying the rows it scrolls and drawing those it wrote, each batch one `damage`. The wheel scrolls the view back through the ring, three rows a step, and a drag of its scrollbar's slider, or a press on its strip, as far as it goes, as any toolkit scroller's, and Shift-Page Up and Shift-Page Down a page of rows, drawn from the cells with the toolkit's overlay scrollbar along its right while the view is back or the pointer is over its strip, wider there; Ctrl-Shift-T opens a tab, as the new-tab button does; a key typed brings the view back to the bottom, and output while it is back leaves the view on the rows it shows. A drag of the window's edge or maximizing it resizes it as any toolkit window, the terminal then as many cells as fit, every tab's lines wrapped again at the new width by their marks, the cursor's line kept in view. Its cursor is a line along the last row of a cell, which no glyph uses. Its scenes are in `preview.l0`, painted by its own drawing (`ui_preview_painted`) |
| `cat` | writes the files its arguments name, through the ordinary `open_in`, the initramfs's or a volume's; reports each it can't read, and exits 1 if any |
| `hello` | prints its pid and arguments, and answers a line: its terminal's, its standard input, if it has one (a program `agentd` runs reads none), else typed at the console driver's, or its inittab's stdin |
| `init` | starts the programs its arguments name, from `/` wherever it is (`NAME&` runs one in the background), waits for the rest, and reports each one's status |
| `echo` | a server: registers as `echo` and sends every request's body back |
| `ping` | a client: finds `echo` by name and checks that N requests come back |
| `spin` | loops forever without a call; other processes still run, thanks to the timer |
| `nap` | sleeps for N ms and checks that the time passed |
| `rtc` | a user-space driver for the PL031 real-time clock: it maps the device, sets an alarm, receives interrupt 34 as a message, and acks it. `rtc clock` instead serves `clock`, the time, to whoever asks, and at the start of every minute to each process listening, as `wm` does; it waits for requests and for the kernel's alarm, set for the start of the next minute, so tells it within a second of it, and leaves the interrupt to `rtc`; `set S` sets it, adding what it moved by to the board's count, writing the Pi 5's RTC, and telling every listener at once; `zone` answers the zone the time is shown in and when it next changes, US Pacific time by the US rule (`zone.l0`), the one place every client asks. Its clock is a PL031 where the kernel gives one whose ID registers say so, or else the Raspberry Pi 5's RTC, asked of the firmware through the mailbox (`firmware.l0` over `mailbox.l0`, see [The Raspberry Pi 5](pi5.md#the-raspberry-pi-5)); with neither it says so and exits 0 |
| `eeprom` | the Raspberry Pi 5's bootloader configuration: with no argument, the one running, and with `version` the bootloader's version, asked of the firmware's command line through the mailbox; `show IMAGE` the configuration inside a `pieeprom.bin`; `update IMAGE CONFIG DIR` that image with the file CONFIG as its configuration, written to DIR as `pieeprom.upd` and `pieeprom.sig` for the bootloader to flash itself from (`pieeprom.l0` and `bootloader.l0`, see [The bootloader's configuration](pi5.md#the-bootloaders-configuration)). With no mailbox it says so and exits 1 |
| `virtio-gpu` | a user-space driver for QEMU's virtio-gpu, serving the display protocol as `display` (see [The desktop](desktop.md#the-desktop)). It finds the device among the 32 virtio-mmio transports and sets up its control queue and cursor queue in DMA pages. It makes the screen resource 1 on scanout 0, at the mode the device offers, and builds its backing from the layers' buffers, so the host composes the screen. Its `info` says the scale, 2 on a screen of 2560×1440 or more, or as the boot argument `scale=` says (see [A large screen](desktop.md#a-large-screen)). It keeps every row of the backing, so a `layers` request builds again only the rows a layer that moved, scrolled or changed covers, and writes the backing's runs straight into the queue's memory. A `damage` is a transfer and a flush of that rectangle. The pointer is the device's cursor, resource 2. Its first frame, as soon as the mode is set, is the wallpaper, under every layer it is given until one covers the screen (see [The display](display.md#the-display-protocol)); with none to read, it is black. With no virtio-gpu on the board it says so on stderr and exits 0. It puts commands into both queues as requests come, many in flight at once, and waits for them by its transport's interrupt, each reply sent once its commands are answered, in its request's order (`flight.l0`; see [virtio-gpu](display.md#virtio-gpu)). If the device offers virgl, as QEMU's `virtio-gpu-gl-device` does, it composes the screen on the host's GPU instead: a texture for each buffer and copies of them onto the screen (`gl.l0`, `compose.l0`, `virgl.l0`; see [The desktop](desktop.md#the-desktop)) |
| `hvs` | the Raspberry Pi 5's display driver, a first draft that has shown the desktop, brought up a stage at a time by its argument (`probe`, `list`, `iommu`; none serves; `mode`, `hdmi`, `eof` and `watch` beside them), serving the display protocol as `display` as `virtio-gpu` does (see [The display on the Raspberry Pi 5](display.md#the-display-on-the-raspberry-pi-5)). It reads the monitor's EDID from the firmware (`edid.l0`), sets HDMI0 to the monitor's preferred mode itself, PHY, timings, pixel valve and, past 340 MHz, scrambling over DDC (`hdmi.l0`, `modeset.l0`; the boot argument `hdmi=` chooses otherwise), and takes HDMI0's channel of the BCM2712's HVS at that mode; without HDMI0's regions, an `hdmi=` is asked of the firmware by `SET_TIMING`, after which it keeps the channel on its own two lists, and `hvs` writes its lists over those. Its first frame is the wallpaper, a plane of its own pages under every layer until one covers the screen (see [The display on the Raspberry Pi 5](display.md#the-display-on-the-raspberry-pi-5)). It shows the layers as one display list of planes fetched straight from the clients' pages, each buffer made one run of addresses by the IOMMU in front of the HVS. It answers each restack at once and writes its list in the half of the list memory the channel isn't fetching, moving the channel to it, as soon as the channel has taken the list before, by channel 0's end of frame (`frames.l0`), only the latest screen asked if several came meanwhile, and gives up a forgotten buffer's pages only once no list it may still read names them (`pending.l0`); it counts the frames and which showed each change, telling the ports `frames` names each frame that showed one and each buffer a list left out. A `damage` cleans the damaged rows' pages out of the caches, and the pointer is a plane on top. A rounded layer's corners are cut by its pixels' alpha, which `hvs` writes 0 there (`corners.l0`). It asks the firmware first whether a display was brought up, since the HVS is otherwise unclocked, and makes sure of its clocks (`fw.l0`). With no region over the HVS, as on QEMU, or no monitor on HDMI0 at boot, it says so and exits 0 |
| `audio` | the audio server ([sound.md](sound.md)): it owns the devices its drivers attach (`proto/audiodev.l0`), says which is the default in and out as `/etc/audio` says (`settings.l0`), read again on `reload`, and serves the audio protocol as `audio` to any number of clients: each stream converted and mixed into its output at the output's rate as the driver says there is room, each listener fed what its input hears in the format it asked (`mixer.l0`, `format/pcm.l0`); the chime played once on the first output; a device gone with its driver's detach or exit, a client's streams and listens with its exit |
| `hdmi-audio` | the Raspberry Pi 5's sound driver, which has played a WAV on a board: it attaches HDMI0 to `audio` as `hdmi0` (see [Sound on the Raspberry Pi 5](sound.md#sound-on-the-raspberry-pi-5)) and plays what the server feeds it, IEC958 subframes (`iec958.l0`) into HDMI0's audio FIFO, the MAI, from a ring of DMA pages through channel 6 of the 40-bit DMA controller, `dma40` (`dma40.l0`), with the MAI, the audio packets and the infoframe set up as Linux's vc4 sets them (`mai.l0`), telling the server its room after each period. It waits for `display`, since `hvs` brings HDMI0 up, and plays nothing on a DVI sink. `hdmi-audio probe` reads the channel's and the audio registers, writing none. With no channel, as on QEMU, or no server, it says so and exits 0 |
| `virtio-input` | a user-space driver for QEMU's virtio input devices, started once a device. It keeps the event queue's 16 buffers in a DMA page and takes the device's interrupt as a message. `virtio-input keyboard` finds the device whose name holds `Keyboard`, serves `keyboard`, and sends each key event to every port that asked it to `listen`: a `KeyEvent` of the Linux key code, pressed, released or repeated, the character it types on a US layout, with Shift and Caps Lock, and Ctrl with a letter as its control character, and the Shift, Ctrl and Alt held. `virtio-input tablet` finds `Tablet`, serves `pointer`, and at each report's end sends a `PointerEvent`: x and y, 0 to 32767, and the buttons; before it, if the scroll wheel turned in the report (`REL_WHEEL`, `REL_HWHEEL`), a `WheelEvent` of its steps, down and right positive. With no such device on the board it says so on stderr and exits 0. Its US layout is `keymap.l0`'s, which `usb-hid` shares |
| `pcie` | the PCIe bus's server, `pcie virt`, for QEMU's virt board (see [USB](devices.md#usb)): reads every function of bus 0 through the ECAM, sizes each memory BAR, puts it in the 32-bit MMIO window, turns on memory space and bus mastering, and serves the pci protocol as `pci`: every function, or those of a class, and an MSI for a driver that asks, set up through the function's MSI or MSI-X capability |
| `sdhci` | a driver for SD cards behind SD Host Controllers, `sdhci pci` those `pcie` finds, QEMU's `sdhci-pci`, and `sdhci pi5` the Raspberry Pi 5's microSD slot, `sdio1`, on interrupt 305 (see [The disk](storage.md#the-disk)): it brings each card up, standard or high-capacity, and serves each as the first `diskN` free, all on one port, telling `fs` of each. Blocks move through the controller's buffer into and out of the client's pages, no DMA; it waits on the controller's interrupt, an MSI or else its INTx line, for what is not done at once, and polls a slot with none. A slot with no card, or no controller on the bus, is said so on stderr, and exits 0 |
| `xhci` | the USB host controller driver and USB's core (see [USB](devices.md#usb)): `xhci pci` drives every xHCI `pci` found, `xhci rp1` the Raspberry Pi 5's two DWC3s on RP1. It halts and resets each controller, gives it its DCBAA, scratchpads, command ring and event ring in DMA pages, and runs it; brings up each device on a root port, one at a time, reading its descriptors and setting its first configuration; and serves the usb protocol as `usb`: devices, their descriptors, claims of interfaces, control transfers, and IN endpoints polled, each report a notice to the client that opened it. It takes each controller's interrupt, an MSI it asks `pcie` for or else its INTx line, as a message, and reads that controller's events; with a controller that has none, as RP1's, or whose line another driver has bound, it polls every event ring, every millisecond when idle. Each controller and each device is a line on stderr. Everything it decides is `core.l0`'s and `bus.l0`'s, pure, tested on the host |
| `usb-hid` | the class driver of USB boot keyboards and mice (see [USB](devices.md#usb)), one process serving both, started with no argument: it claims every boot keyboard, sets the boot protocol and SET_IDLE(0), opens its interrupt endpoint, and serves `keyboard`, sending a `KeyEvent` for each key its reports press or let go, with the character `keymap.l0` says and the Shift, Ctrl and Alt of the reports' modifier byte, and repeating a held key itself, 500 ms then every 33 ms, timed by the kernel's alarm; and claims every boot mouse and serves `pointer`, sending a `PointerMotion` of each report, and QEMU's `usb-tablet`, by QEMU's vendor id, sending a `PointerEvent` of each, after a `WheelEvent` if its wheel turned. Each name has a port of its own, and it waits on both and the usb server's with a set of ports. It drives no device, and needs no `dev` line |
| `usb-audio` | the class driver of USB Audio Class 1.0 devices (see [Isochronous endpoints](devices.md#isochronous-endpoints)), one process for all, and a driver of `audio`: it reads each device's audio function (`format/uac.l0`), says its streams in the log, and attaches each, in and out, to the server as `usb-VID:PID-KIND` ([sound.md](sound.md#usb-devices)): a stream in set going at the rate the server asks, or the nearest it takes, its isochronous packets passed on as they come, in the device's own format; a stream out set going at the rate the server starts it at and fed from a ring shared with `xhci`, into which the server's frames go, widened to the device's samples, the server told the room every 10 packets. A device unplugged is detached. It claims an interface only while it uses it, drives no device, and needs no `dev` line; `/etc/system` starts it after `audio` |
| `speech` | the speech service ([speech.md](speech.md#the-speech-service)), started after `agentd` by `/etc/system`: it reads Whistle from `/Volumes/data/speech/whistle.cact`, or `-m MODEL`, waiting up to 10 s for the volume, and with no model says so in the log and exits 0; grabs F12, or `-k CODE`, of `wm`; and serves `speech` (`proto/speech.l0`), waiting on its port, the key's and the microphone's at once. The key held, `audio`'s default input is heard, at 16 kHz of one channel, until it is let go; tapped, until the speaker is quiet (`endpoint.l0`), 30 s at most; the phrase made text by `whistle_transcribe` and said to `agentd` as `say speech`, held and asked again each second while a turn runs. `speech listen`, `stop`, `hear PATH` and `mute on\|off` ask the service running, waiting a minute for it to register; a refusal on standard error, exit 1 |
| `virtio-blk` | a user-space driver for QEMU's virtio-blk, serving the disk protocol as the first `diskN` free, `disk0` in the demo, and telling `fs` (see [The disk](storage.md#the-disk)). It finds the device, reads its capacity from its config, and sets up its request queue in one DMA page. Each `read` or `write` it checks against the disk's size and the pages the client shared, then has the device move the sectors straight into or out of those pages, a descriptor a page, and waits for the device's interrupt, on a port of its own, for 30 seconds at most, after which it takes the disk to have stopped answering and fails every request. It accepts FLUSH, for `flush`, and RO, refusing a read-only disk's writes itself. With no virtio-blk on the board it says so on stderr and exits 0 |
| `virtio-net` | a user-space driver for QEMU's virtio-net, serving the nic protocol as `nic` (see [The network](network.md#the-network)). It finds the card, takes its address from its config, sets up its receive and transmit queues in DMA pages, and takes its interrupt as a message: each frame the card takes it tells every port that asked it to `listen`, and each frame it is sent it copies into its transmit buffer and waits for the card to take. With no virtio-net on the board it says so on stderr and exits 0 |
| `gem` | the Raspberry Pi 5's network driver, a first draft that has run nowhere, serving the nic protocol as `nic` as `virtio-net` does (see [The network on the Raspberry Pi 5](network.md#the-network-on-the-raspberry-pi-5)). It drives RP1's Cadence GEM and the BCM54213PE PHY behind it over MDIO, takes the board's address from the firmware through the mailbox, and waits on the GEM's interrupt, RP1's MSI-X vector 6, and the kernel's alarm, which looks at the link every half second; it polls its rings only if the interrupt cannot be had. With no RP1 on the board, as on QEMU, it says so and exits 0 |
| `virtio-rng` | a user-space driver for QEMU's virtio-rng, the entropy device, which draws on the host's `/dev/urandom`, serving the random protocol as `random` (see [Randomness](devices.md#randomness)). It finds the device, sets up its one queue of 8 entries in a DMA page, and for `bytes N` offers the device a buffer to fill, again until it has N, waiting for each as `virtq_wait` does. With no virtio-rng on the board it says so on stderr and exits 0 |
| `rng200` | a user-space driver for the Raspberry Pi 5's random number generator, the BCM2712's RNG200, serving the random protocol as `random` as `virtio-rng` does (see [Randomness](devices.md#randomness)): it turns the generator on as Linux does if it is off, and for `bytes N` waits for it to be warm and takes words from its FIFO, restarting it once on a failed health test. With no RNG200 it can open, as on QEMU's board, it says so in the log and exits 0 |
| `inet` | the IPv4 stack, `inet dhcp` or `inet [ADDR/PREFIX [GATEWAY [DNS]]]`: the address, netmask, router and name server a DHCP server gives it, its lease renewed and rebound as the clock's minutes pass, or those given, 10.0.2.15/24 behind 10.0.2.2, with 10.0.2.3 as the name server, by default (see [The network](network.md#the-network)): a client of `nic`, which answers ARP and ICMP echo requests, keeps the neighbours ARP finds, routes to the link or the gateway, gives UDP datagrams to the clients bound to their ports, and sends their datagrams and echo requests, and keeps their TCP connections, each one's data put in a ring of pages shared with its owner, serving the inet protocol as `inet`. With no `nic` within 5 seconds it says there is no card and exits 0 |

The libraries are in `common/`, shared by the kernel, every program and
the host tools, and in `user/lib/`, grouped by what they are: `sys/`, the
kernel's calls and what programs do alike; `proto/`, the protocols of
the servers, as their clients speak them; `format/`, data as bytes,
pure, which the host tools link too; `gfx/`, drawing; and `ui/`, the
toolkit. Each is linked into every program (`ULIB`), or into those that
need it, by the Makefile's `LIBS_` lists. L0 has one namespace, so a
name in a library is taken in every program that links it.

| Library | What it holds | Linked into |
